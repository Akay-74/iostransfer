# IOStransfer — Architecture (draft v0.5)

iPhone → PC bulk photo/video transfer. Built for moving thousands of assets per session, choosing them by
built-in collections, with optional "move" (cut/paste) that deletes from the iPhone only after the PC has a
verified copy on disk.

Status: draft for cross-review. Open disagreements are marked **[DEBATE]**.

---

## 0. Hard constraints (from the user)

| Constraint | Consequence |
|---|---|
| iPhone → PC only | One-way data; PC sends only control messages |
| Wi‑Fi first, USB later | Session layer must not care who opened the TCP connection (§3.1) |
| PC = Windows + Linux | Rust receiver, single codebase |
| Untouched originals | No transcoding anywhere; HEIC/HEVC/DNG byte-for-byte |
| Photos and Videos are separate sections | Separate UI tabs, separate send lanes, separate output folders |
| iCloud Photos must be OFF | Prerequisite; still checked at runtime (§2.6) |
| $0 budget, no Mac | GitHub Actions macOS runners (public repo) → unsigned .ipa → sideload with free Apple ID |

Implications of free Apple ID: 7-day re-sign, max 3 sideloaded apps, 10 App IDs/week, no App Groups / push /
iCloud entitlements → **single app target, no extensions** (no share extension, no Live Activity widget).

## 2. iPhone app

### 2.1 Module split (so most logic builds and tests on Linux)

```
ios/
 ├─ TransferCore/          Swift Package, NO Apple-only imports (no CryptoKit, no Network)
 │    Frame codec, message types (Codable), SenderSession state machine
 │    (bytes in / bytes out, transport-agnostic), lane scheduler, selection rule model,
 │    journal (SQLite via system libsqlite3, present on Linux too)
 │    SHA-256/HMAC via swift-crypto (`import Crypto` = CryptoKit on Apple platforms)
 │    → `swift test` on Linux, plus an interop test vs the Rust receiver
 ├─ InteropSender/         Linux CLI: TransferCore + plain POSIX/Foundation socket, sends a folder
 └─ App/                   iOS-only, kept thin
      PhotoLibraryService, ResourceReader, ConnectionService (Network.framework),
      Pairing (AVFoundation QR scanner), GridViewController, TransferScreen,
      DeleteService, LogForwarder
      project.yml → generated by XcodeGen on CI (never hand-edit .pbxproj on Linux)
```

Normative for the Swift side: **docs/TRANSFERCORE.md**. It's a sans-I/O core: `SenderCore.handle(Event) -> [Action]`
is synchronous and deterministic, and time, randomness and the journal are injected. The App's `SessionDriver`
and `InteropSender` are thin drivers that perform Actions. Two traps the spec calls out:
- Foundation's `JSONDecoder` is lenient about a BOM and possibly invalid UTF-8, so `IOSTWire` pre-checks every control
  payload (vectors `control_bom`, `control_invalid_utf8`).
- Two-phase pairing: the core emits `storeSecret`, the driver writes the Keychain and reports `secretStored`,
  and only then does the core emit PAIRED. A driver must never send PAIRED on its own.

### 2.2 Collections

- Photos tab: `smartAlbumUserLibrary` (Recents), Favorites, Screenshots, Selfies, Live Photos, Portrait
  (`smartAlbumDepthEffect`), Panoramas, Bursts, RAW, Long Exposure, Animated, plus user albums
  (`.album`, `.albumRegular`) and folders.
- Videos tab: Videos, Slo-mo, Time-lapse, Cinematic, Screen Recordings, Spatial (when present).
- Each tab's fetch uses a mediaType predicate so Videos never appear in Photos and vice versa.
  A Live Photo is a **photo** (its paired MOV travels with it, not in the Videos tab).
- Empty smart albums are hidden. Counts come from `PHFetchResult.count` (no enumeration).

### 2.3 Selection model (no materialised per-asset state)

```swift
enum SelectionRule {
    case collection(id: String)                                     // "all Screenshots"
    case range(collection: String, from: Boundary, to: Boundary)    // tap start → tap end
    case dateRange(collection: String, from: Date, to: Date)
    case assets(Set<String>)                                        // individual taps
}
struct Boundary { let date: Date; let assetID: String }
struct Selection { var include: [SelectionRule]; var exclude: Set<String> }
```

- **Range select**: enter Range mode, tap first, scroll (fast scroller with month labels), tap last.
  Indices come from `PHFetchResult.index(of:)`; count is `|i-j|+1 − excluded`. Ends can be tapped
  in either order. Range mode over an already-selected area removes it from the selection instead.
- Cell highlighting is O(1): "index within any range of this collection, or in assets-set, and not excluded".
- Boundaries store date and ID; if a boundary asset is deleted, fall back to the stored date.
- **SelectionResolver** turns rules into a lazy, creation-date-ordered stream of assets. An asset matched by
  two rules is sent once (a Set of seen IDs costs a few MB even at 100k).
- Bursts: fetch with `includeAllBurstAssets = true` when resolving (we send every frame; untouched originals).

### 2.4 Grid

- `UICollectionView` + compositional layout + `PHCachingImageManager` (≈200 px, `.fastFormat` first then
  `.opportunistic`), caching window = visible ± 2 screens. **Not SwiftUI LazyVGrid** (falls over at 10k+).
- Drag-to-select (like Photos), section headers per day/month with "select all" for that section.
- System picker (`PHPickerViewController`) is never used for bulk. Optional "quick pick" uses it with
  `photoLibrary: .shared()` and reads `assetIdentifier` only, never loading the data it offers.

### 2.5 Unit of transfer: the PHAsset

An asset is committed (ACKed, eligible for delete) only when **all of its resources** are durable on the PC.
Resources come from `PHAssetResource.assetResources(for:)`:

| Resource type | Sent? | Notes |
|---|---|---|
| `.photo` | ✅ | The original |
| `.fullSizePhoto` | ✅ if present | Edited render |
| `.adjustmentData` | ✅ if present | Edit recipe (.AAE plist) |
| `.alternatePhoto` | ✅ | RAW of a RAW+JPEG pair |
| `.pairedVideo` / `.fullSizePairedVideo` | ✅ | Live Photo motion part (original / edited) |
| `.photoProxy` | ❌ | Not an original |
| `.video` / `.fullSizeVideo` | ✅ | Original / edited video |
| `.adjustmentBaseVideo`, `.adjustmentBasePairedVideo`, `.adjustmentBasePhoto` | ✅ if present | Needed to make edits reproducible |
| Unknown or new types | ✅ | Send everything except proxies; never drop silently |

**[DEBATE] Edited renders.** The peer proposed original + adjustmentData by default, with the render optional.
I keep the **render ON by default**. On Windows and Linux an .AAE file can't be applied by any tool, so
without the render the user's edits are effectively invisible on the PC, and after a move they're gone from
the phone too. Option "Skip edited renders" exists for copy jobs that want to save space.

Rationale: for **move**, anything we don't send is lost forever. Sending all non-proxy resources is the only
rule that's safe by construction. Slo-mo, Cinematic and Spatial store their extra data inside the resources
listed above (or as extra resources of the same types), so "send all non-proxy resources" covers them.
The M2 spike must log the resource list of real Slo-mo, Cinematic, ProRAW, Portrait and Spatial assets to confirm.

### 2.6 Reading resources

**Bounded spool** (changed in v0.2 after review):
`requestData`'s `dataReceivedHandler` pushes at PhotoKit's pace, with no backpressure and no
offset/range API, so streaming straight to the socket either buffers without limit (multi-GB videos run out
of memory) or can't resume.

```
PhotoKit ──writeData(for:toFile:)──► spool/<asset>/<res_key>   (Application Support/spool, excluded from backup)
spool file ──read 256 KiB at offset──► SHA-256 ──► socket     (true backpressure, real offset resume)
ACK durable ──► delete spool/<asset>/
```

- `PHAssetResourceManager.writeData(for:toFile:options:)` with `isNetworkAccessAllowed = false`, into
  `spool/<job>/<sha256(localIdentifier)>/<res_key>.tmp`, renamed to `<res_key>` in the completion handler.
  A `.tmp` is never sent. Identifiers contain `/`, hence the hash. The spool dir uses
  `FileProtectionType.completeUntilFirstUserAuthentication` (readable while locked, after the first unlock).
- The spool is freed on **ACK**, not on send, so its size is bounded by the unacked window (§3.4), not
  only by in-flight slots. Typically < 200 MB; the worst case is one huge video.
- Free-space guard: `volumeAvailableCapacityForImportantUsage`. Before exporting, require size hint + 2 GB
  reserve. Otherwise that asset fails with "Free X GB to send this video". It isn't deleted, and the rest of the job continues.
- Exact file size is known before RES_BEGIN, so progress bars are exact and the protocol can carry the size.
- The spool lives in Application Support (not Caches/tmp, which iOS may purge), so after an app kill an
  existing spool file is resumed at the PC's offset, with no re-export.
- Startup sweep: delete spool dirs whose asset isn't in the journal's in-flight set.
- "Needs network" errors mean the asset is still in iCloud, so iCloud is (partly) on. That asset is marked
  `notLocal` and skipped; any move is blocked, and the onboarding warning is shown again.
- SHA-256 via CryptoKit, computed while reading the spool file for sending.
- Concurrency: exporters (2 photo + 1 video) feed senders (3 photo slots + 1 video slot, §3.6).
  `NWConnection.send` completion gates the next read.
- Later optimisation, only if the R1 spike shows export I/O is the bottleneck: photos under 50 MB via
  `requestData` into memory (bounded size), skipping the spool.
- Thermal: watch `ProcessInfo.thermalState`; at `.serious` drop to 1 photo + 1 video lane, at `.critical` pause.
- Size hint before export (for the free-space check only): best-effort `resource.value(forKey: "fileSize")`
  (private KVC, harmless for a sideloaded app).

### 2.7 App lifecycle and backgrounding

- Default: foreground transfer, `isIdleTimerDisabled = true`, big "keep this screen open" UI and a dimmed
  "pocket mode" overlay to save battery.
- On `willResignActive`: `beginBackgroundTask` (≈30 s) to finish in-flight resources, collect ACKs and flush the journal.
- Journal = SQLite in Application Support (PROTOCOL §8.3: job, job_asset, delete_batch, delete_item).
  A JSON rewrite per ACK would be O(n²) at 100k assets. Writes are batched every 1 s.
  If the app is killed, it restarts the job and NEED skips what's already done.
- Keychain items (`device_id`, `device_secret`) use `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`,
  otherwise reconnecting while locked fails. The service name is derived at runtime, never from a hardcoded
  bundle ID (SideStore may append the team ID).
- **[DEBATE] Opt-in background keep-alive.** Since we never go through App Store review, we can set
  `UIBackgroundModes = audio` and play a silent `AVAudioSession` (`.mixWithOthers`) during a transfer, so it
  keeps running when the screen is locked. It's off by default and labelled experimental. Risks: battery,
  interruptions from calls and other audio (we resume on `interruptionEnded`), and the OS may still kill the
  app under memory pressure (the journal covers that). Unknowns for the spike: is this background mode allowed
  with a free signing profile (expected yes: it's an Info.plist key, not an entitlement), and can we read
  Photos data while the device is locked (expected yes after the first unlock)? If either fails, we stay
  foreground-only. Expect lower throughput while locked (Wi‑Fi power save).
- Background `URLSession`: rejected. It needs files on disk, which doubles storage use and duplicates the transfer engine.

### 2.8 Move (cut/paste) flow

Normative: PROTOCOL §6.4 (VERIFY), §8.2 (per-asset states), §8.4 (delete phase), §10 (crash matrix). Summary:

```
transfer → ACK durable → VERIFY(current resource keys + sizes [+ sha256], modified_ms) → VERIFIED ok
        → pre-delete guards → delete_batch row committed → ONE performChanges { deleteAssets } → system prompt
```

- Requires `.readWrite` authorization with **full** access (`.limited` → move disabled, explain why).
- Pre-delete guards, all must pass, otherwise the asset is dropped from the batch and kept:
  VERIFIED < 10 min old; asset still exists; `canPerform(.delete)`; `sourceType == .typeUserLibrary`
  (one undeletable asset fails the whole change block); not `notLocal`; **content unchanged since VERIFY** (§3.3).
- Assets that were "already on the PC" (NEED `have`) are verified without re-export: the PC checks the
  phone's *current* resource list, so an asset that gained an edit since the last copy can't be deleted
  before the edit is transferred.
- Batch size: start with one `performChanges`. If the R4 spike shows it hangs at large N, use batches of 2,000 (one prompt each).
- Done screen: "N items moved to Recently Deleted. X GB is freed after you empty Recently Deleted
  (Photos → Albums → Recently Deleted)." Recently Deleted is a 30-day safety net.
- If the user cancels the prompt, the batch becomes `declined` and a banner offers "Delete N transferred items" again.
- **Metadata-only edits (v0.4).** "Adjust Date & Time" and "Adjust Location" change only the Photos database,
  not the resource bytes, so the original's EXIF keeps the old values. After a move, the correction would exist nowhere.
  - The fingerprint includes the asset `meta` = `created_ms`, `fav`, `loc` (PROTOCOL Δ18), so the guard notices these changes.
  - File name and mtime already use `PHAsset.creationDate`.
  - **Move jobs always write an XMP sidecar** (`<base>.xmp`, about 1 KB) for every asset, kept in sync with `meta`.
    (v0.5: we no longer compare with the file's EXIF first. That would need HEIC/DNG/MOV metadata parsers on the PC,
    which means more dependencies and more attack surface on untrusted input (THREAT_MODEL), only to save a 1 KB file.
    Since the XMP holds PhotoKit's values, which are the user's corrected truth, writing it always is also the more correct choice.)
    XMP rather than our JSON because darktable, digiKam, Lightroom and exiftool read it automatically, and the
    original stays byte-for-byte untouched. Fields: `exif:DateTimeOriginal` + `exif:OffsetTimeOriginal` (from
    `tz_min`), `exif:GPSLatitude/Longitude/Altitude`, `xmp:Rating` = 5 if favourite. Copy jobs write XMP only with
    `--xmp` (the phone still has the truth). `--sidecars` adds the JSON on top.
  - Pre-delete guard mismatch (e.g. the user favourites a photo while the move is running): the asset is **re-VERIFIED
    once** automatically (the PC refreshes the XMP), then it joins the delete batch. Only a second mismatch drops it, with a visible reason.

## 3. Protocol (v1)

**docs/PROTOCOL.md is normative** (byte-exact framing, messages, state machines, timeouts, crash matrix).
This section records only the architectural decisions and why they were made.

### 3.1 Roles

- **Connection role** (who dials) and **session role** (who sends) are independent.
  - Wi‑Fi: PC listens (port 47800, Bonjour), phone dials.
  - USB (M6): phone listens (`NWListener`, 47801), PC dials through usbmuxd.
- Session roles are always: phone = Sender, PC = Receiver.
- Security:
  - Wi‑Fi: TLS 1.3 with the PC as TLS server; the phone pins the PC's SPKI.
  - USB: plain TCP over the cable + HMAC mutual auth (PROTOCOL Δ13, decision in M6). Network.framework can't
    act as a TLS client on an accepted connection, and a phone-side TLS identity adds a lot of complexity for a local cable.
- Auth: HMAC-SHA256 challenge/response over `device_secret` in both directions, the same on every transport.
  The secret is sent only once, at pairing, inside pinned TLS.

### 3.2 Discovery and pairing

- PC advertises `_iostransfer._tcp` (Rust `mdns-sd`, pure Rust, no Apple Bonjour needed on Windows). TXT `pcid`, `v`.
- iOS Info.plist: `NSLocalNetworkUsageDescription`, `NSBonjourServices = [_iostransfer._tcp]`, `NSCameraUsageDescription`.
- `iostransfer pair` prints a QR code (and saves a PNG):
  `iost://pair?pcid=<uuid>&h=<ip1,ip2>&p=<pairing port>&rp=<receive port, default 47800>&spki=<base64url, no padding, 43 chars>&t=<one-time token>&n=<pc name>`.
  `p` is the `iostransfer pair` session (any free port, so pairing works while `receive` runs); the phone stores `rp` for every later transfer.
  The QR is only ever read by the app's own scanner. The app does **not** register an `iost://` URL scheme
  (THREAT_MODEL N10), otherwise any web page or message could trigger pairing with an attacker's PC.
- **Pairing confirmation (N11):** both screens show a pairing code (first 40 bits of the SPKI pin, Crockford
  base32, e.g. `7K3M-Q9TX`; PROTOCOL §4.1), and the PC asks `Pair "Ana's iPhone"? [y/N]` before committing.
  The host list excludes Docker, Hyper-V, WSL, VPN and link-local adapters.
- PC key is **ECDSA P-256**. The SPKI pin is the SHA-256 of the constant 26-byte P-256 SPKI prefix + the 65-byte point
  from `SecKeyCopyExternalRepresentation`. Any other key type fails closed.
- Two-phase pairing (WELCOME carries the secret → phone stores it → PAIRED → PC commits) so neither side is half-paired.
- If Bonjour fails, the phone tries the QR's IPs, then a manual IP entry.

### 3.3 Decisions and their reasons

| Decision | Reason |
|---|---|
| Custom framed protocol, not HTTPS | USB reverses who dials (HTTP would need the phone to be the server = a second design). ACK and VERIFIED are server pushes on a live session. Mitigation for "can't curl it": `--dump-frames`. |
| One TLS connection, multiplexed by slot | One TCP stream normally fills Wi‑Fi on a LAN. Revisit only if R2 shows < 80% of iperf3. |
| JSON control frames + binary DATA (`slot, u64 offset, bytes`) | Easy to debug; control traffic is tiny. |
| Phone reads from a spool, exact `size` in RES_BEGIN | PhotoKit `requestData` has no backpressure or offset (§2.6). |
| Unit of commit = PHAsset (all resources) | Delete safety for Live, edited, RAW+JPEG. |
| Identity = `(device_id, localIdentifier, res_key)`; `modified_ms` only a hint | modificationDate changes on favourites and album edits; as part of the identity it would duplicate files. |
| Resource **families**: originals never re-requested; edits re-checked through `adjustment_data` hash → `NEED_MORE` | A favourite toggle doesn't re-send a 4 GB edited video, yet real edits are caught. |
| **Content fingerprint instead of exact modificationDate for move guards** (v0.3) | See below. |
| SHA-256 everywhere (CryptoKit / swift-crypto / Rust `sha2`) | Hardware accelerated on both sides; no extra dependency. |
| Timestamps in ms UTC + **per-asset** `tz_min` | Names don't depend on the PC's timezone. See below for why per-asset. |

**Per-asset `tz_min` (v0.3, change to PROTOCOL Δ6).** The phone's *current* offset is wrong for every photo taken
during the other half of the DST year (off by one hour), and for photos taken while travelling.
Use `TimeZone.current.secondsFromGMT(for: creationDate) / 60` per asset, which is DST-correct.
Travel is still approximate: the true offset is only in EXIF `OffsetTimeOriginal` and QuickTime `creationdate`,
and the PC can't read those before RES_BEGIN fixes the name. Acceptable for v1, since the file contents are untouched anyway.

**Move guard: content fingerprint, not exact `modified_ms` (v0.3, change to PROTOCOL §6.4/§8.4).** Developers report
that PHAsset.modificationDate also changes from system activity (Photos' background analysis, viewing), not
only from user edits. If that's true, "`modified_ms` must equal the verified value" would silently drop
assets from deletes, or make VERIFY report `stale` in a loop. Instead:

- Fingerprint = sorted list of `(res_key, size)` + sha256 of `adjustment_data#0` if present (tiny export).
- VERIFY sends the fingerprint.
- The pre-delete guard recomputes it and compares.
- `modified_ms` stays as the cheap trigger for "recompute the fingerprint now".

This is spike R9. If modificationDate turns out to be stable, the exact check can come back as an extra guard.

### 3.4 Lanes and scheduling

- Photo lane 3 slots, video lane 1 slot. Idle lanes lend their slots. 256 KiB chunks, round-robin between busy slots.
- Order inside each lane is creation date, so an interrupted transfer leaves a coherent prefix.
- Windows: `WELCOME.max_unacked_assets/bytes` from the PC. The phone uses `min(PC value, its own spool budget)`,
  where the spool budget = min(2 GB, 10% of free space).
- **Reconnect cost (v0.3):** after a reconnect, the sender restarts the job from page 0.
  - In a **copy** job, assets the journal already marks `acked` for this `(pc_id, store_id)` are left out of the
    re-sent MANIFEST, so a 100k job doesn't re-run `assetResources(for:)` for everything after every Wi‑Fi blip.
  - In a **move** job, the same applies until the VERIFY phase, which re-reads the current resources anyway.
  - Spike R10 measures `assetResources(for:)` per-asset cost.

## 4. PC receiver (Rust)

### 4.1 Crates

`tokio`, `tokio-util` (LengthDelimitedCodec), `rustls` + `tokio-rustls`, `rcgen` (ECDSA P-256 self-signed cert, generated once, stored in the config dir),
`mdns-sd`, `rusqlite` (bundled, WAL), `serde`/`serde_json`, `sha2` (no `asm` feature: it breaks Windows MSVC; SHA-NI is used at runtime anyway), `filetime`, `qrcode`
(terminal output), `clap`, `tracing`, `directories`.

### 4.2 Durable write path

Normative: PROTOCOL §9 (states `partial → verified → done`, 64 MiB fsync checkpoints, crash matrix P1–P6).

- `.part` file → every 64 MiB: fsync + commit `durable_offset` (resume offsets come only from checkpoints;
  after a power loss, bytes past the last fsync may be garbage, NTFS especially).
- `RES_END`: hash ok → fsync file → commit `verified` → rename (Linux `rename` + fsync dir; Windows
  `MoveFileExW(REPLACE_EXISTING | WRITE_THROUGH)`) → commit `done`. Startup recovery finishes any `verified` rows.
- SQLite: WAL + `PRAGMA synchronous=FULL` (with `NORMAL`, WAL commits are not durable and the ACK would lie).
- ACK durable only when every key in `ASSET_END.res_keys` is `done`.
- **I/O isolation (v0.3):** the socket reader never blocks on disk.
  - DATA goes into a bounded per-session write queue (e.g. 64 MiB) served by a blocking-pool writer.
  - When the queue is full, the reader stops reading (TCP backpressure slows the phone down).
  - While self-throttled, the receiver's peer-dead timer is **suspended**. The phone's frames are sitting in
    our own socket buffer, unread, so the 30 s silence rule would otherwise make the PC time out on itself
    during a long fsync on a slow HDD. PINGs from the PC keep flowing on the writer side, so the phone stays happy.
- Supersede: a new session for the same device waits until the old session's writers have shut down (fsync .part,
  commit offsets) before computing NEED (PROTOCOL §9.3).
- Disk space: checked before each RES_BEGIN. If less than 1 GB + size is free → `PAUSE{disk_low}` and a CLI warning.

### 4.3 Layout and naming

```
<dest>/<DeviceName>/Photos/2025/03/20250314_101522_IMG_4821.HEIC
                                   20250314_101522_IMG_4821.MOV          (Live Photo motion)
                                   20250314_101522_IMG_4821_edited.JPG   (fullSizePhoto; extension from its UTI)
                                   20250314_101522_IMG_4821.AAE          (adjustmentData)
                                   20250314_101522_IMG_4821.DNG          (RAW alternate)
<dest>/<DeviceName>/Videos/2025/03/20250314_103001_IMG_4830.MOV
```
- Base name = phone-local creation time (`created_ms` + per-asset `tz_min`) + `originalFilename` stem of the
  primary resource. It's **allocated once per asset** under a per-destination mutex inside a DB transaction, so all
  resources share the same base and the same `_2` suffix (Live Photo pairing survives collisions).
- Collisions are compared **case-insensitively** (NTFS, exFAT, FAT, also when mounted on Linux).
- Extensions come from each resource's UTI, not its filename (`FullSizeRender` can be JPEG when the original is HEIC).
- `--layout collection`: `<dest>/<DeviceName>/<JobLabel>/YYYY/MM/…`.
- Name cleanup: strip `<>:"/\|?*` and control characters, avoid reserved Windows names (`CON`, `NUL`, …),
  and trim trailing dots and spaces. Paths over 240 characters use the `\\?\` prefix.
- mtime (and creation time on Windows via `SetFileTime`) = the asset's creation date.
- Security requirements for the writer (THREAT_MODEL N6–N8, N16): extensions come from a UTI allowlist, never from
  `original_filename`; a canonical-prefix check runs after every path join; `asset_id` never appears in paths;
  `.part` files are created with `create_new` and never follow symlinks or reparse points; `RES_BEGIN.size` ≤ 1 TiB and ≤ free space;
  the key file and index.db are owner-only, or the receiver refuses to start.
- `--sidecars`: `<base>.json` with favourite, subtypes, dimensions, burst ID and job label. No per-asset album
  list (PROTOCOL Δ7). Later option: build an album → assets map once per job by fetching each user album
  (cost ∝ total memberships, not 100k reverse lookups) and send it as one `ALBUMS` frame in protocol v2.
- The PC never deletes user files. Resources the phone no longer lists become `orphaned` in the DB.

### 4.4 DB schema

Normative: PROTOCOL §9 (`resources.state ∈ partial | verified | done | orphaned`, `durable_offset`).
Paired devices are **not** in index.db. `devices(device_id, name, secret, paired_at)` stores the **raw** 32-byte
secret (the HMAC check needs it), so it lives in `<config dir>/devices.db` next to the TLS key, both owner-only
(THREAT_MODEL N16/N16a). The destination is often an exFAT drive or NAS share where permissions can't be
enforced, and it travels with the photos. index.db holds no secrets.
Plus `meta(key PRIMARY KEY, value)` holding **`store_id`** (uuid, created with the index; sent in `WELCOME.store_id`).
The phone's "skip acked on reconnect" is bound to `(pc_id, store_id)`. A new `--dest`, or a deleted `.iostransfer/`,
gives a new store_id, so the phone clears its acked marks and re-checks everything (PROTOCOL Δ16).
Stored at `<dest>/.iostransfer/index.db`, next to the files, so moving the destination folder keeps the index valid.

### 4.5 CLI

```
iostransfer pair                     # QR code in terminal + PNG, waits for the phone
iostransfer receive --dest PATH [--layout date|collection] [--sidecars] [--port 47800] [--paranoid]
iostransfer devices | status | verify [--rehash]
iostransfer receive --insecure-dev   # plaintext, localhost only: interop tests
```
GUI (Tauri, same core crate) comes after the protocol is proven.

### 4.6 Platform notes

- **Windows Firewall**: the installer (Inno Setup, free) adds inbound rules for `iostransfer.exe`: **TCP 47800 and
  UDP 5353** (without UDP 5353, mdns-sd advertising silently fails and only QR/IP pairing works). On start,
  the CLI checks the rule (`netsh advfirewall firewall show rule`) and prints the exact fix command if it's missing.
- Windows Defender slows writes of thousands of new files. The README suggests a folder exclusion; we also
  keep writes large (1 MiB buffer).
- Windows SmartScreen "unknown publisher" (no paid code signing): documented "More info → Run anyway".
- Linux (Fedora/Nobara): the firewalld `FedoraWorkstation` zone allows 1025–65535 and mDNS by default; for
  other distros we print the `firewall-cmd`/`ufw` command. mDNS coexists with avahi (SO_REUSEADDR on 5353).

## 5. Build and distribution ($0)

```
.github/workflows/
  core.yml   ubuntu: swift test (TransferCore) + cargo test + interop test
             (Swift sender CLI on Linux ↔ Rust receiver, --insecure-dev, folder of sample HEIC/MOV)
  ios.yml    macos-latest: xcodegen → xcodebuild -sdk iphoneos CODE_SIGNING_ALLOWED=NO
             → Payload/IOStransfer.app → IOStransfer.ipa (artifact; release on tag)
  pc.yml     matrix ubuntu + windows: cargo build --release → artifacts (+ Inno Setup on Windows)
```
- The repo must be public (unlimited standard runner minutes; private repos get ~200 macOS minutes a month).
- **Recommended install path (Linux or Windows)**: `iloader` (github.com/nab138/iloader, RPM for Nobara, needs
  the `usbmuxd` + `fuse` packages) over USB once → installs **SideStore** and writes the pairing file →
  SideStore installs our `.ipa` from the GitHub Release URL and **refreshes it on the phone every week over
  Wi‑Fi via LocalDevVPN** (no PC trip). Fallback: iloader direct install, repeated weekly.
- Install as a real app, **not inside LiveContainer** (PhotoKit permissions and the delete prompt inside a
  container host are untested).
- **Bundle ID is fixed forever** (`io.github.<user>.iostransfer`) so we never burn extra App IDs (10 per 7 days).
  At runtime the code never assumes it, because SideStore re-signing may append the team ID.
- iPhone: Developer Mode on (Settings → Privacy & Security).
- Use a **dedicated free Apple ID** for SideStore, not the user's main account: the sideload tools handle its
  credentials, and a separate account limits the damage if one is compromised.
- Known fragility: Apple sign-in changes periodically break SideStore refresh, and pairing files die when the
  phone is untrusted, restored, or sometimes after iOS updates. This is the most fragile part of the system. The README has a recovery section.
